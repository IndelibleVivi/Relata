# Research Foundation Integration Review

**Status:** completed for repository initialization  
**Objects reviewed:** the extracted foundation material and the original Relata Target Architecture Draft 0.1  
**Authority:** this review records integration choices; current project authority remains in `STATUS.md`, `CHARTER.md`, `ASSUMPTION_REGISTER.md`, governance, and accepted decisions

## Verdict

The foundation was a strong starting package, but it still read as a delivered “bootstrap bundle” rather than the living Relata repository. Its research-first pivot, adversarial review, assumption register, case method, and first pilot were retained. Transitional instructions, ambiguous terminology, architecture-shaped templates, incomplete consent operations, and a structure-only checker were revised before adoption.

No named-source claim from Draft 0.1 was independently verified during repository integration. Those claims remain research candidates until pinned Evidence Cards support them.

## Findings and resolutions

| ID | Finding | Resolution |
|---|---|---|
| F-01 | README and Start Here described unpacking, Git initialization, and a prebuilt bundle as future work | Rewrote them as current repository entrypoints with three immediate research tasks and no commit/publication instruction |
| F-02 | `Research Bootstrap`, `R0`, and project identity could blur together | Standardized the project as `Relata`; current phase is `R0 — Research Foundation` |
| F-03 | `participant` referred both to people and technical systems | Current authority now uses `community contributor / co-researcher` for people and `system under study` for technical systems |
| F-04 | `oracle` could imply total evaluator-owned relationship truth | Replaced current case language with `probe evidence contract` and `reference-context baseline`; the original draft wording remains historical |
| F-05 | Consent Levels resembled a progression and lacked an executable record | Reframed them as independent per-contribution modes and added a restricted consent-record template |
| F-06 | System Card and Pressure Map templates assumed ordered events, retrieval, rendered context, and explicit operations | Rewrote them to begin in system-native vocabulary and distinguish native, emulated, opaque, unsupported, unknown, and not applicable |
| F-07 | The source map assumed an existing external audit was available and authoritative | Kept AML as a first candidate while requiring exact public re-pinning before any conclusion enters Relata |
| F-08 | Evidence workflow did not define claim states, read coverage, review, transfer, or supersession | Added an operational source workflow and claim ledger to the Evidence Card contract |
| F-09 | Pilot working artifacts had no concrete record form or local path | Added a pilot record template and an ignored artifact-packet layout |
| F-10 | The checker validated required files but not internal Markdown links or premature project shells | Replaced it with `tools/check_repo.py` and broadened repository checks |
| F-11 | Status prose could make templates and plans sound like completed research | Added a zero-based evidence ledger and explicit template/seed/clinic-ready/accepted distinctions |

## Material retained and strengthened

- long-term adult human–AI intimacy as a legitimate primary domain;
- relationship-local norms rather than one universal intimacy style;
- the longer causal question from retained history through response use and repair;
- required use and prohibited resurfacing as separate concerns;
- architecture pluralism as an empirical pressure-test obligation;
- counterfactual twins and the Memory Necessity Gate;
- community members as co-researchers with no raw-chat requirement;
- Pilot 001’s exact current-turn identity and disjoint historical condition;
- visible disagreement, evaluator ambiguity, and repair-oriented evidence.

## Material rewritten rather than adopted verbatim

- all root onboarding and status material;
- source/evidence workflow and Evidence Card lifecycle;
- consent, attribution, withdrawal, and restricted-record handling;
- System Census vocabulary and templates;
- case terminology and baseline names;
- Pilot 001 execution record;
- repository verification and repo-local agent contract.

## Material rejected or deferred

Relata does not currently adopt:

- an event-sourced canonical relationship world as the system ontology;
- four permanent evaluation tracks;
- system-under-study APIs;
- a benchmark runner, SDK, services, or hosted infrastructure;
- immutable artifact spines and exact digest contracts before an executable boundary exists;
- composite scoring, a model-judge panel, Arena, or Leaderboard;
- 100–300-session worlds as a validity requirement;
- public/sealed/operations repository splitting without an actual secret or operations boundary;
- Draft 0.1’s 22 “locked” decisions as a binding architecture.

## Remaining research uncertainty

The integration does not establish construct validity, architecture neutrality, case validity, reviewer agreement, or a lawful/ethical protocol for a future formal human-participant study. It establishes the repository surfaces needed to investigate those questions without pretending they are solved.
